# أفكار قابلة للتنفيذ — Actionable Ideas

هذا الملف يجمع الأفكار المستقبلية القابلة للتنفيذ التي تُستخلص من مراجعات خارجية أو جلسات نقاش، قبل اعتمادها رسمياً في خطة التطوير (`AGENTS.md` ← «التالي بالترتيب»).

كل بند يُعنوَن **باسم المهارة المصدر** وتُوثَّق تحته عناصر ثابتة:

1. **الفكرة** — ماذا نفعل بالضبط، وكيف تعمل آلياً.
2. **الاستفادة** — لماذا تستحق، وأي فجوة تغلق.
3. **الملفات المستهدفة للتحديث** — نقاط التعديل الحقيقية في المستودع.
4. **الروابط** — المصدر الذي استُخلصت منه الفكرة.

عند تنفيذ بند يُوسم «منفَّذ» مع الإشارة إلى الالتزام/الفرع؛ وإن فقد جدواه يُحذف مع السبب.

## 1. `token-saver-context-compression` (alias لـ `context-compressor`)

**الفكرة المستخلصة:** وسم حماية معلَن (Declared Protection Tag)
**الحالة:** مقترح — لم يُنفَّذ

### الفكرة

`protectedEnd` في `lib/optimizer/arabic-normalizer.ts` يخمّن المناطق المحمية حالياً (سياج Markdown، backticks، JSON، روابط، اقتباسات، سطور كود حرّ). الفكرة: إضافة وسماً **يُعلنه المستخدم بنفسه** داخل البرومبت ليفرض حماية حتمية على أي نص، بغض النظر عن شكله — مثلاً:

```
راجع الكود التالي وحسّنه:
<keep>
def calculate(x):
    return x ** 2 if x > 0 else None
</keep>
ثم لخّص النتيجة في جملة واحدة.
```

سلوك مقترح:

- `<keep>...</keep>` — المحتوى بين الوسمين يمرّ حرفياً بلا تنقية ولا إعادة صياغة، **والوسمان نفسهما يُستهلكان** (لا يظهران في المخرج النهائي).
- وسم غير مغلق → يحمي حتى نهاية النص (الاتفاقية نفسها المعتمدة للمقاطع غير المغلقة).
- داخل سياج كود أو اقتباس يُعامَل كنص عادي — لأن `protectedEnd` يمسح يساراً→يميناً، فيصل للسياج أولاً ويحسمه قبل الوسم.
- اختيار الصياغة (`<keep>` أو `««ثابت»»` أو غيرها) قرار يُحسم عند التنفيذ؛ المعيار: سهولة الكتابة للمستخدم العربي وعدم التصادم مع markup شائع.

### الاستفادة

- **تغلق بنداً مفتوحاً في الخطة:** البند 3 في «التالي بالترتيب» — «توسيع تصنيف المقاطع؛ تبقى الصيغ الأقل شيوعاً غير مغطاة». بدل ملاحقة أنماط كود غير معروفة إلى الأبد، يصبح للمستخدم مخرج حتمي يضمن الحماية بنفسه.
- **نية معلنة > تخمين:** الكاشف الحتمي يظل يعمل للحالات الشائعة، والوسم يغطي ما يعجز عنه — طبقتان متكاملتان لا بديل عن بعضهما.
- **تكلفة تنفيذ صغيرة:** امتداد لماسح موجود (`protectedEnd`) لا مسار جديد؛ لا تبعيات ولا نموذج إضافي.
- **يزيد الثقة في وضع mock المحلي:** المناطق الحساسة تُحمى حتى عند غياب مفتاح API أو فشل النماذج.

### الملفات المستهدفة للتحديث

| الملف                                     | التعديل                                                                                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `lib/optimizer/arabic-normalizer.ts`      | إضافة فرع في `protectedEnd` يتعرف وسم الفتح `<keep>` ويعيد موضع نهاية `</keep>` (أو نهاية النص عند غيابه)، مع شريط الوسمين من المخرج. |
| `lib/optimizer/arabic-normalizer.test.ts` | حالات: وسم مغلق يُحفظ حرفياً؛ وسم غير مغلق يحمي للنهاية؛ وسم داخل سياج يُعامَل نصاً؛ محتوى الوسم لا يُنقّى ولا تُستهلك كياناته.       |
| `README.md`                               | توثيق الوسم للمستخدمين (صيغة، مثال، قاعدة غير المغلق).                                                                                |
| `AGENTS.md`                               | عند التنفيذ: نقل البند من «التالي بالترتيب» إلى «مُنجَز» وتحديث وصف `protectedEnd`.                                                   |

## 2. `context-compression` (muratcankoylan/agent-skills-for-context-engineering)

**الفكرة المستخلصة:** قياس التوفير بالتوكن لكل مهمة، لا لكل طلب
**الحالة:** مبدأ حاكم — لا تنفيذ فوري

### الفكرة

المقياس الصحيح للضغط ليس «توكن الطلب الواحد» بل **«التوكن لكل مهمة»**: إجمالي ما يُستهلك لإنجاز المهمة شاملاً تكلفة إعادة المحاولة ورداءة المخرجات. ضغط يوفّر 30% لكنه يفقد معنىً يرفع التكلفة الكلية لا يخفضها. عند TOSO: تقرير التوفير الحالي (أصل → منقّح → نهائي) يقيس الطلب الواحد — يبقى صحيحاً، لكن أي إشارة «نجاح مهمة» مستقبلية (قبول المستخدم للمخرج، غياب إعادة التشغيل) تُوزن على هذا الميزان لا على التوفير المجرد.

### الاستفادة

- بوصلة صدق تمنع المنتج من مطاردة أرقام توفير عالية على حساب جودة المخرج — مبدأ يحكم قرارات عدوانية التعليمات واختيار النماذج مستقبلاً.
- إطار جاهز عند سؤال «هل التوفير المعروض حقيقي؟»: إذا لم تنجُ المهمة، فالتوفير اسمي لا فعلي.

### الملفات المستهدفة للتحديث

لا تعديل فوري — مبدأ يحكم القرارات المستقبلية. عند التفعيل يمسّ:

- `lib/types.ts` — حقول تقرير إضافية لإشارة نجاح المهمة إن أُضيفت.
- مكوّن بطاقة التوفير في `components/` — إبراز إشارة النجاح بجانب نسبة التوفير.

### الروابط

- المستودع: https://github.com/muratcankoylan/agent-skills-for-context-engineering
- المهارة (فقرة «Optimize for Tokens-Per-Task, Not Tokens-Per-Request»): https://github.com/muratcankoylan/agent-skills-for-context-engineering/blob/main/skills/context-compression/SKILL.md

## 3. `context-compression` + `advanced-evaluation` + `evaluation` (muratcankoylan/agent-skills-for-context-engineering)

**الفكرة المستخلصة:** حكم نية بالمجسّات الوظيفية بدل تقييم الجودة العام — يحسم البند 2 المعلّق في «التالي بالترتيب»
**الحالة:** مقترح — لم يُنفَّذ

### الفكرة

استبدال «حكم نموذجي على الجودة» الغامض بـ**مجسّات وظيفية موجّهة** بعد التنقية: «هل البرومبت المنقّح ما زال يطلب المهمة الفلانية؟ هل بقي الشرط/النفي؟ هل نجا المخرج المطلوب؟» — فحص اتساق وظيفي محدد لا تقييم مفتوح. وعقد الحكم النموذجي يُصمَّم كالتالي:

- **reference-based**: مقارنة الناتج بالأصل (فرع الترجمة/التلخيص في تصنيف التقييمات) لا تقييم مستقل للنص.
- **الدليل قبل الدرجة**: إلزام الحكم باقتباس العنصر الذي تحقق منه قبل إصدار أي درجة.
- **نموذج حاكم مختلف عن المولّد**: تفادي تحيّز self-enhancement.
- **أبعاد متعددة لا درجة واحدة**: نية / كيانات / قيود / أسلوب — تُسجَّل منفصلة.
- **اشتغال انتقائي**: الفحوص الحتمية (entity-guard، quality-guard) أولاً، والحكم يُطلق على الحالات الملتبسة فقط — ضبطاً للتكلفة.
- شكل النتيجة `{sufficient, score, evidence, dimensions}` — متسق مع فلسفة الرفض الصادق المعتمدة في المشروع.

### الاستفادة

- يحوّل البند 2 في «التالي بالترتيب» من فكرة مؤجلة إلى تصميم قابل للتنفيذ: جسر بين `quality-guard` الظاهري والحكم الدلالي.
- المجسّات قابلة للاختبار حتمياً (حالة تعرف الجواب الصحيح مسبقاً) بعكس الحكم المفتوح.
- يصدّق الخيار المعماري القائم: «فحوص حتمية قبل الحكم النموذجي» هو الترتيب الموصى به في المصدر نفسه.

### الملفات المستهدفة للتحديث

| الملف                                       | التعديل                                                               |
| ------------------------------------------- | --------------------------------------------------------------------- |
| `lib/optimizer/intent-judge.ts` (جديد)      | مجسّات النية + عقد الحكم `{sufficient, score, evidence, dimensions}`. |
| `lib/optimizer/intent-judge.test.ts` (جديد) | حالات معروفة الجواب: مهمة محذوفة، شرط مفقود، نفي مقلوب، مخرج سليم.    |
| `lib/services/optimization-service.ts`      | استدعاء انتقائي للحكم على الحالات الملتبسة بعد الحارسين الحتميين.     |
| `app/api/optimize/route.ts`                 | تمرير نتيجة الحكم واختيار النموذج الحاكم (مختلف عن المولّد).          |
| `AGENTS.md`                                 | تحديث البند 2 في «التالي بالترتيب» عند التنفيذ.                       |

## 4. `advanced-evaluation` + `evaluation` (muratcankoylan/agent-skills-for-context-engineering)

**الفكرة المستخلصة:** صرامة مقارنات A/B في `compare-instructions.mjs` — تحيّز الموضع والتقسيم بالتعقيد
**الحالة:** مقترح — لم يُنفَّذ

### الفكرة

رفع صرامة سكربت مقارنة التعليمات عند استخدام حكم نموذجي على مخرجات النسخ:

- **مقارنة بترتيبين متعاكسين**: تمرير مخرجَي النسختين (A/B ثم B/A) للحكم، وإعلان التعادل عند اختلاف الحكمين — يزيل position bias من أي ادعاء «v3 أفضل من v2».
- **تحقق حتمي مسبق**: قبل الحكم النموذجي، فحص أن المرشحين يحققان نفس المخطط ويحفظان الكيانات — فشل حتمي سريع قبل صرف توكنز الحكم.
- **تقسيم حالات الاختبار بالتعقيد**: بسيط / متوسط / معقد / معقد جداً، مع تقرير نتيجة لكل شريحة بدل متوسط واحد يخفي الفشل.
- **عتبة حجم**: 20–30 حالة في التطوير المبكر، و50+ لإشارة موثوقة قبل اعتماد نسخة.

### الاستفادة

- الادعاءات المقارنة تصبح صامدة أمام تحيّز الموضع والطول — نفس التحيّزات الموثقة التي أسقطت أحكاماً سابقة.
- التقسيم يكشف _أين_ تخفق التعليمة (اللهجة؟ النصوص الطويلة؟ المحتوى التقني؟) بدل رقم إجمالي — يوجّه الجولة التالية من التحسين مباشرة.

### الملفات المستهدفة للتحديث

| الملف                                  | التعديل                                                                 |
| -------------------------------------- | ----------------------------------------------------------------------- |
| `scripts/compare-instructions.mjs`     | إضافة تمرير مزدوج بترتيب متعاكس + تصنيف الحالات بالتعقيد عند تعريفها.   |
| `Docs/reports/instruction-compare*.md` | قالب التقرير: نتيجة لكل شريحة تعقيد + حكم التعادل عند اختلاف الترتيبين. |
